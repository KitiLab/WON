## 1. The Three Forms of Language Independence

A fundamental governance commitment of the WON project is that **Go is a temporary bootstrap scaffolding language, not the permanent foundation of WON.**

To avoid conflating distinct architectural milestones, WON formalizes three distinct tiers of independence:

```
                            Three Forms of Independence
                                         │
        ┌────────────────────────────────┼────────────────────────────────┐
        ▼                                ▼                                ▼
Tier A: Language Independence   Tier B: Implementation Independence   Tier C: Backend Independence
• Own grammar, types, semantics • Permanent compiler written in WON   • Emits machine code directly
• Own AST and Typed IR (TIR)    • Go compiler retired completely      • GCC/Clang retired (LLVM/QBE)
• Already achieved in design    • Target: Phase 2 / Phase 3           • Target: Phase 5 / Phase 7
```

1. **Tier A — Language Independence**: WON has its own unique syntax, formal grammar, type system, ownership rules, and runtime model. It is not a transpiler DSL or a thin wrapper around another runtime.
2. **Tier B — Compiler Implementation Independence**: The production compiler toolchain (`won`) is written 100% in WON itself. Building, running, and contributing to the WON compiler requires zero Go tooling.
3. **Tier C — Backend Independence**: The native code generation pipeline produces machine code directly (via an integrated LLVM or QBE backend) without requiring an external C compiler (GCC or Clang).

> [!IMPORTANT]
> **Tier B (Go Retirement) does NOT require Tier C (GCC/Clang Retirement).**  
> The self-hosted WON compiler can initially emit standard ISO C11 code, allowing Go to be completely retired from the development workflow while continuing to leverage GCC/Clang for native machine code optimization.

## 2. The Four-Stage Bootstrap Pipeline

The transition from the Go bootstrap compiler to a self-hosted WON compiler is executed across four verified stages:

```
 Stage 0 (Current)               Stage 1                         Stage 2                         Stage 3
 ┌─────────────┐                 ┌─────────────┐                 ┌─────────────┐                 ┌─────────────┐
 │  wonc0 (Go) │ ──compiles───►  │  wonc1 (WON)│ ──compiles───►  │  wonc2 (WON)│ ──verifies──►  │Reproducible │
 │  Bootstrap  │                 │  Executable │                 │  Executable │                 │ Bootstrap   │
 └─────────────┘                 └─────────────┘                 └─────────────┘                 └─────────────┘
        ▲                               ▲                               ▲                               ▲
        │                               │                               │                               │
  Written in Go                 Written in WON                  Written in WON                  Identical Output
```

### Stage 0 — The Trusted Bootstrap Compiler (`wonc0`)
- **Implementation**: Written in Go (`compiler/poc/`).
- **Role**: Compiles the initial subset of WON required to build the new compiler.
- **Identity**: Branded internally as `wonc0` (or `wonc-bootstrap`).
- **Preservation Policy**: Kept in the repository as a historical verification artifact and emergency recovery mechanism.

### Stage 1 — The WON Compiler Written in WON (`wonc1`)
- **Implementation**: The complete compiler frontend, type checker, TIR pipeline, and C code generator are implemented in WON source code (`compiler/wonc/`).
- **Build Process**: `wonc0` compiles `compiler/wonc/` into a native executable: `wonc1`.

### Stage 2 — Self-Compilation (`wonc2`)
- **Build Process**: `wonc1` compiles its own source code (`compiler/wonc/`):
  ```bash
  ./bin/wonc1 build -o bin/wonc2 compiler/wonc/main.won
  ```
- **Validation**: `wonc2` must successfully compile the complete standard library and test suites.

### Stage 3 — Reproducible Verification and Convergence
- **Convergence Verification**: `wonc2` is used to compile the compiler source once more, producing `wonc3`.
- **Equivalence Assertion**: The intermediate C code generated by `wonc1` and `wonc2` **MUST** be byte-for-byte identical (or semantically identical modulo timestamps and random build hashes):
  $$\text{IR}(\text{wonc2}) \equiv \text{IR}(\text{wonc3})$$
- Once convergence is proven, the compiler has achieved self-hosting integrity.

## 3. Language Capabilities Required for Self-Hosting

To implement a production-grade compiler in WON, the language must support a specific, pragmatic subset of systems programming capabilities. The matrix below defines the implementation prerequisites:

| Subsystem / Capability | Needed for Compiler? | Specific Language Construct Required | Target Milestone |
| :--- | :--- | :--- | :--- |
| **String & Text Processing** | **Mandatory** | `String`, `&str`, UTF-8 slicing, `.split()`, formatting | Phase 1B |
| **Dynamic Collections** | **Mandatory** | `Vec[T]` (dynamic array/vector) with push, pop, index | Phase 1B |
| **Associative Maps** | **Mandatory** | `HashMap[K, V]` for symbol tables and interned strings | Phase 2A |
| **Nominal Structs & Enums** | **Mandatory** | Algebraic data types for AST and TIR node representation | Phase 1B |
| **Pattern Matching** | **Mandatory** | `match` expressions with destructuring for AST traversal | Phase 2A |
| **Recursion & Functions** | **Mandatory** | Lexical closures, recursive calls for recursive-descent parsing | Phase 1B |
| **Generics & Collections** | **Mandatory** | Parametric polymorphism for `Vec[T]`, `Option[T]`, `Result[T, E]` | Phase 2A |
| **File I/O & Filesystem** | **Mandatory** | Reading source files, writing generated C/native files, directory walk | Phase 1B |
| **Process Execution** | **Mandatory** | Spawning GCC / Clang / LD processes and capturing stderr | Phase 1B |
| **Structured Diagnostics** | **Mandatory** | JSON serialization for AI agent integration and error formatting | Phase 2B |
| **Error Propagation** | **Mandatory** | `Result[T, E]` and `?` operator for clean parser error recovery | Phase 1B |
| **Modules & Namespaces** | **Mandatory** | Multi-file package organization for compiler passes | Phase 1B |
| **Memory Arenas** | **Recommended** | `Arena[T]` for high-speed AST allocation and zero-cost teardown | Phase 2B |
| **C Interoperability** | **Mandatory** | Calling `libc` (`malloc`, `free`, `exit`, `clock_gettime`) | Phase 1B |
| **Advanced Concurrency** | Optional | Multi-threaded parallel file compilation (can be single-threaded initially) | Phase 3 |

## 4. Objective Go Retirement Criteria

The Go bootstrap compiler (`wonc0`) **SHALL NOT** be removed from primary developer documentation or build pipelines until all of the following ten criteria are empirically satisfied:

1. [ ] **Complete WON Source**: The WON compiler is fully implemented in WON source code under `compiler/wonc/`.
2. [ ] **Stage 1 Success**: `wonc0` compiles `compiler/wonc/` into a working `wonc1` binary without manual intervention.
3. [ ] **Stage 2 Success**: `wonc1` compiles its own source into `wonc2`.
4. [ ] **Stage 3 Convergence**: `wonc2` compiles `compiler/wonc/` into `wonc3`, and the generated outputs match deterministically.
5. [ ] **Full Test Suite Pass**: `wonc2` passes 100% of the unit, integration, and language specification test suites.
6. [ ] **Parity Benchmarks**: The self-hosted compiler compiles source code at equal or faster throughput than the Go bootstrap compiler.
7. [ ] **Clean Developer Setup**: Standard developer installation (`make install` or prebuilt native binaries) requires zero Go SDK installation on the host.
8. [ ] **CI Pipeline Independence**: The primary CI build matrix compiles the compiler using the previous release's native WON binary, without invoking `go`.
9. [ ] **Documented Disaster Recovery**: A standalone bootstrap archive (containing either `wonc0` or pre-generated C bootstrap files) is published with verified build instructions from pure C.
10. [ ] **Owner Sign-Off**: Formal review and authorization from the KitiLab project owner.
